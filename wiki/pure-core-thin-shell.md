# Pure core, thin shell

The factory's proven product architecture: **a deterministic, seeded, IO-free/DOM-free logic core holding all rules, plus the thinnest possible interface shell.** Every shipped prototype follows it, and it is why adversarial verification works here at all.

- Games: [groupline](prototype-groupline.md) (`core.js` — validation, guess-checking, session reducer; 539 tests), [chainfall](prototype-chainfall.md) (`core.js` — cascade resolution, chain scoring, seeded RNG; a scripted 40-drop playthrough verified the fun *end-to-end from tests alone*), and [foldup](prototype-foldup.md) (`core.js` — the pure `fold` half-plane reflection, XOR `combine`, exact-equality `checkWin`, and the `solveMinFolds` BFS par oracle over a certified level bank; the FLIP animation is the only thing the shell adds).
- Apps: [settleup](prototype-settleup.md) (pure `core.py`, exact integer-cent arithmetic, the CLI is one thin IO layer), [subscription-sleuth](prototype-subscription-sleuth.md) (load→normalize→cluster→detect→render pipeline of pure functions), [tidy](prototype-tidy.md) (classify/plan/apply seams), [sediment](prototype-sediment.md) (`build_events`→`detect_eras`→`caption_era`, three pure functions over immutable metadata event records with an injectable `now`; the `os.stat` walk is the only IO).

Consequences worth remembering at ideation time:

- **Testability gates feasibility.** Ideas whose fun/value lives in *tuned feel* (suika physics, pinball flippers, onebeat) repeatedly get docked to feasible≤3 because the core can't certify the experience — the tests can't see the part that matters. Ideas with a crisp pure core (FreeCell, broughlike, 2048) score feasible=5. [foldup](prototype-foldup.md) scored feasible=9: its entire mechanic (`fold`, `combine`, `checkWin`) is a set of pure grid transforms with hand-verified reference cases, and its *difficulty/fairness* (par) is certified by a `solveMinFolds` BFS oracle **that lives in the core**, so the tests assert the content is honest without a browser — a solver-in-the-core is the strongest form of "certify from tests alone" ([solver-verified generation](solver-verified-puzzle-generation.md)). The one thing the tests can't see — whether the fold *feels* like paper — is exactly what ships v0-pending-playtest.
- **Seeded determinism is a feature, not just a test convenience** — reproducible deals/boards enable "share this exact puzzle," daily seeds, and replay, which the [daily-ritual](daily-puzzle-rituals.md) demand pattern values.
- **A pure core over immutable input can re-explain any output for free.** Because every view is a pure re-derivation from the same source, a new "why is this number what it is?" view costs almost nothing — it reuses the existing functions and reconciles by construction. [settleup](prototype-settleup.md)'s `--breakdown` landed by reusing `split_expense`/`compute_balances` unchanged; [sediment](prototype-sediment.md)'s month-sparkline and era blocks are both pure folds over the *same* ordered event stream, so a new timeline view is free (the dossier calls this the re-derivation principle, and the [dev-mechanic transplants](dev-mechanic-transplant.md) all exploit it — "blame is just a fold over ordered diffs"); [subscription-sleuth](prototype-subscription-sleuth.md)'s **price-change detection is the same shape** — a merchant's price history is a *step function over the date-ordered charges*, so detecting a hike is one more pure fold over the series the clusterer already builds, and both the row's run-rate and the hike's +$/yr bite route through the single `annualize` function (no divergent factor). The [declarative ledger vs. running tab](declarative-ledger-vs-running-tab.md) page traces why a mutable running-tab model (Splitwise) cannot do the same. **Caveat the re-derivation principle exposed:** ordered-in-time segmentation is essential where value-clustering would lie — a price that goes $10→$12→$10 (a reverting promo) is *one level with one anomaly* in date order, but two "levels" to a value-clusterer; the fold must be over the ordered series, with a sustain-count guard so a lone outlier never mints a spurious step.
- **Choosing the domain event record decides what's testable.** Sediment's core receives already-computed `(event_time, name, ext, size)` tuples, so the messy timestamp policy (`min(birthtime, mtime)`, the Linux `st_birthtime`-`AttributeError` trap) lives in ONE thin-shell seam and the core stays filesystem-free and deterministic — the same discipline that lets `subscription-sleuth` unit-test cadence detection without a CSV. Push the platform mess to the edge; keep the core pure over plain records.
- The browser feel gap that this architecture leaves (the shell's animation/interaction layer) is now covered by the playtest verify lens over localhost — so "feel-heavy" ideas are *less* penalized than they were when only the core was verifiable.
