# Lessons (coroner-maintained)

Every builder, verifier, and brief-writer must read and obey the **checklist below** before working; consult the appendix entry only when a rule fires on your work (each appendix entry carries the failure class, worked examples, and the exact guard pattern). The coroner appends new rules to BOTH the checklist and the appendix, keeps their numbering aligned, and retires rules that stop firing. Note: prototype scaffolds in `templates/` pre-encode rules 1, 3, 12, 14, and 21 — new prototypes built from them start compliant.

## Checklist (obey all; numbers match the appendix)

1. One documented, cwd-independent, cold-start run command per prototype (a wrapper script that resolves its own dir).
2. Never claim tests pass without running them — include the real command output.
3. No hardcoded absolute paths; derive paths from the prototype's own directory.
4. Every user-facing entry point handles empty and garbage input with one clean error line + non-zero exit, never a traceback.
5. Verifiers and test fixtures use fresh per-run temp dirs (`mktemp -d`); never a shared or fixed scratch path.
6. Fail safe when a plain file already occupies a needed directory name — clear error, nothing moved.
7. Anything the tool reads back that it earlier wrote (manifests, configs, caches) is UNTRUSTED: validate full shape at the parse boundary, wrap the whole read+interpret step.
8. Containment-check any persisted path before using it to move/write/delete (`resolve()` + `relative_to()` under the intended root).
9. Never order records by raw filename when the real key is structured (timestamp+counter) — parse the key and sort by that.
10. Enforce value/shape invariants at the domain constructor every path goes through, not only at one parser.
11. Every implemented capability is DEMONSTRATED by the headline one-command run over the committed sample, with a test pinning the sample's coverage.
12. Docs that assert code facts (symbols, "N tests" counts) are bound by regression tests — across ALL docs quoting the fact, symbol-shaped tokens defined wide; brief-required new symbols need a POSITIVE `REQUIRED_DOC_SYMBOLS` check (mention-gated scans can't see an omitted paragraph).
13. When a mutation commits synchronously but the re-render is deferred, freeze AND visibly disable the ENTIRE input surface for the gap; pin with a fake-DOM regression test plus a non-vacuous, handler-anchored strip-the-guard self-check.
14. A headline runtime property automation can't exercise (offline-from-disk at `file://`) is pinned by a STATIC invariant test on the artifact with a self-check; carry no raw `http(s)://` literal even inside a data: URI (percent-encode it).
15. An optional curated field, when PRESENT, must be non-empty and well-formed — reject the vacuous form (`bait: {}`); omission stays legal.
16. Curated strings the user reads back (names, labels, path segments) need HYGIENE beyond anti-traversal: reject surrounding whitespace and non-printable/control chars at the domain gate; ordinary internal spaces stay legal.
17. A mode that provably never reads an optional input (an `--undo`/repair escape hatch) must not be gated on that input validating — dispatch it before loading.
18. Tolerate benign, unambiguous editor artifacts (leading BOM, CRLF) at the parse boundary — valid content should succeed; genuinely malformed content still errors.
19. A doc's frozen copy of real command output is bound to the real output by a byte-exact test; any normalized-away line (paths, timestamps) gets its own semantic assertion; an EXCERPT that shows only some blocks and elides the rest "for brevity" is bound PER SHOWN BLOCK (each shown block `==` the real renderer's block for that key), not left unbound because the fence ≠ the full output.
20. A wrapping "next X" selector that can return the current position must map wrap-to-self to a DISABLED control at the UI seam (one shared helper for both render and click).
21. In a bundler-less single-file artifact, every declared function must be referenced — guard with a static dead-code scan with both-way self-checks.
22. Doc prose must not claim a STRONGER invariant than the test/code enforces ("byte-for-byte" vs canonical-JSON) — word the doc to the actual check or strengthen the check.
23. A headline doc example must not depend on a tool the pitch promises not to require (`jq` in a stdlib-only project) — pair it with a stdlib fallback and test that the pairing holds.
24. A shipped feature must leave the catalog's "next step" column (INDEX row + dashboard card) the same heartbeat it ships — checked at heartbeat step 5.
25. Any index derived from an event field or geometry read can be NaN/Infinity: gate with `Number.isInteger(idx) && 0 <= idx < n` at EVERY entry point, bail before storing into cursor state, and read cursor state back through a safe coercer.
26. Any output that emits ONE unit per step across a data-DERIVED range (a per-month/day/bucket sparkline, timeline, histogram, or table spanning min..max of a field) must be BOUNDED — one outlier value (a stray 1970-epoch mtime, a far-future date, a huge id) otherwise floods the output with hundreds/thousands of near-empty rows; cap the count and fold the remainder into one honest summary row (never silently drop it), with a regression test that a stray outlier keeps the output ≤ the cap and accounts for every item.
27. When a HOST-level condition (full disk/ENOSPC, no network for git, a dead sandbox) blocks the WRITE-dependent tooling a verifier leans on (Bash's own `.output` capture, git, node, Playwright's temp profile), don't hard-fail and don't delete anything outside the factory tree to force it — fall back to Read-only structural verification, record the degradation + which checks could not run honestly, and FLAG the host for a future heartbeat; and prefer a byte-level invariant that a NO-TOUCH content non-goal is provable via the prototype's OWN test (`node test_core.js`) rather than only via `git diff`, so verification survives degraded tooling.
28. A pointer hit-test that resolves a click to one of TWO INTERSECTING targets by nearest-distance (`vDist <= hDist`) mis-resolves at the exact crossing (both distances tie) — refuse the ambiguous tie as a no-op, aim any test/probe center-helper OFF the crossing so every input round-trips, and pin with a UI test on the sharpest (2x2) board that both axes drive correctly + the exact crossing is refused + no level becomes unreachable.

## Appendix — full rules with worked examples

1. Every prototype runs with ONE documented command from a cold start; if setup is needed, the run command is a script that performs the setup. The documented cold-start command must be cwd-independent (a wrapper script that resolves its own dir), not a bare `python3 foo.py` that only works from inside the prototype folder.
2. Never claim tests pass without having run them — include the actual command output in your report.
3. No hardcoded absolute paths in prototype code; derive paths from the prototype's own directory.
4. Every user-facing entry point must handle empty and garbage input gracefully — verifiers try that first.
5. Verifiers and test fixtures must use isolated, per-run temp directories (`mktemp -d` / `tempfile.mkdtemp`), never a fixed shared scratchpad subfolder. Concurrent factory processes sharing one path cross-contaminate each other's files and produce false-alarm failures.
6. A tool that creates output directories must fail SAFE when a plain (non-directory) file already occupies a needed directory name: `mkdir(exist_ok=True)` still raises `FileExistsError` in that case. Catch it, emit a clear one-line error that names the offending path, exit non-zero, and move/overwrite/delete nothing — never a bare traceback or a half-applied run. (This is the general "a name I need for a folder is already a file" class; applies to any sort/export/build step.)
7. Any data the tool reads back from disk that it earlier wrote (manifests, undo logs, caches, saved config, state files) is UNTRUSTED input: it may be hand-edited, truncated, or corrupt. Validate its full shape at the parse boundary — not just the container, but every element's type and required keys — and route every failure through the same clean-error path (one line, non-zero exit, no mutation), never a bare traceback. Wrap the whole read+interpret step (parse AND the code that indexes into the parsed structure) in the error handler, not just the `json.load`. (General "persisted-state is untrusted on read-back" class; a downstream `entry['key']` that assumes a shape the validator didn't enforce is the classic escape.)
8. When a persisted path is read back and used to MOVE, WRITE, or DELETE (e.g. an undo/restore manifest's `from`/`to`, a config-supplied output path), enforce containment BEFORE acting: resolve the path (collapsing `..`, following symlinks; `Path.resolve()` works on non-existent paths) and assert it is under the intended root via `relative_to()`. Skip-and-report anything that escapes; never let a `../` in stored/edited data relocate a file outside the tree the user pointed at. (General "stored relative path can traverse out" class; the tool need not ever write such a path itself for a tampered/corrupt one to reach this code.)
9. Do not order records by a RAW filename (or any raw string) when the real ordering key is structured — e.g. an embedded UTC timestamp plus a same-second disambiguation counter. ASCII byte order betrays you: `-` (0x2D) sorts before `.` (0x2E), so `x-2.json` sorts before `x.json` and a "latest" lookup silently returns the OLDER record. Parse the structured key out (timestamp, counter) and sort by that. (General "lexical filename sort ≠ chronological order" class; bites any newest-wins/most-recent lookup over timestamp-named files.)
10. Enforce a value/shape invariant at the DOMAIN boundary (the constructor / factory that every code path goes through), not only at the parser or one importer. If the parser normalizes (e.g. `abs()` on an amount, clamping a range, canonicalizing a key) but `SomeType.__init__` does not, then any other caller — a test helper, a future importer, a REPL, a second input format — can construct an object that silently violates the invariant, and downstream aggregation (`sum`, `total`, a count) produces a wrong-but-not-crashing result. The tests won't catch it if they only assert the invariant on parser-produced objects. Push the check down into the constructor and add a regression test that builds the object DIRECTLY (bypassing the parser) with a violating value. (General "invariant guarded only at one gate the domain trusts" class; the classic escape is a `_txn(...)`-style helper that hands a raw value straight to `__init__`.)
11. If a capability is implemented and unit-tested, it must also be DEMONSTRATED by the headline one-command run (`./run.sh` over the committed sample/fixture) — otherwise a user who runs only that command never sees it, and the sample silently under-covers the feature set. When you add a mode/branch/cadence/category to the classifier, add a matching row to the committed sample so the default run exercises it, and add a regression test that asserts the sample surfaces the FULL advertised range (e.g. exact-set equality over the produced labels), so a later edit that drops one from the sample fails loudly. (General "tested-but-not-demonstrated capability" class; keep the README's shown sample output in sync with the real output too.)
12. Agent-native docs (`CLAUDE.md`, `.claude/skills/**/SKILL.md`) that assert a fact ABOUT the code — a symbol name ("core logic lives in `build_plan`"), a test count ("42 tests"), a category/flag list — will silently rot when the code moves and the doc doesn't. Prefer a regression test INSIDE the prototype that recomputes the fact from the source of truth and asserts the doc matches: cross-check every code symbol the docs name against the actual module (`hasattr`), and check any quoted "N tests" against the live `TestLoader().discover()` count. Make the check non-vacuous (assert it flags a deliberately-wrong doc) and keep it robust to prose backticks (only symbol-shaped tokens, plus a small curated list of the bare single-word functions). Where a per-prototype test can't reach (e.g. a claim spanning multiple files), at minimum keep the number/name honest and reword frozen literals to point at the command that regenerates them. Two escape modes to close up front, not rediscover: (a) scan the count/fact literal in EVERY doc that quotes it — not just the agent-native map docs. If `README.md` and `BRIEF.md` also say "N tests", they rot identically, so a doc-set for the count check must be all-of-them (a `_DOCS_WITH_COUNTS` covering README/BRIEF too), separate from the narrower symbol-mapped set — and the count regex must tolerate an adjective ("N passing tests", "N green tests"), which a bare `\d+\s+tests?` misses. (b) Define "symbol-shaped token" WIDE — an identifier that has an underscore OR mixes letter case — not as a whitelist of a few naming conventions; a convention-list (lowercase-snake + PascalCase only) silently misses leading-underscore SCREAMING_SNAKE constants (`_PREFIX_RE`) and mixed-case renames (`classify_cadence_RENAMED`), so the auto-scanner ends up narrower than "any symbol-shaped token" and a rename slips past whatever isn't in the curated list. (General "orientation docs drift from the code they describe" class; distinct from rule 11's sample/README-output sync — this is about the CLAUDE.md/SKILL.md map, not the demoed run.) COROLLARY — a MENTION-GATED docs-vs-code scan is structurally BLIND to an entirely-OMITTED new capability. The natural shape of the rule-12 check is "for every code symbol the docs ALREADY name in backticks, assert it exists in the module" — a NEGATIVE check that only fires on symbols the docs mention. It therefore cannot catch the failure where a whole new feature ships and the docs simply never name its symbol at all: the loop never iterates over a token that isn't there, so the missing paragraph passes GREEN while the deliverable is absent (exactly how Groupline's v1 share grid — `buildShareGrid`/`DIFFICULTY_EMOJI`/`state.guesses` — shipped with the code+tests+UI correct but README/CLAUDE.md/SKILL.md never describing it, and the §7 scan staying green because it only checked already-named symbols). When a brief REQUIRES a specific new capability be documented (the "extend the docs-vs-code check so the new symbol can't silently rot" clause), the check must be POSITIVE, not mention-gated: maintain an explicit `REQUIRED_DOC_SYMBOLS` list and assert at least one agent-native doc NAMES each required symbol (in backticks), with a non-vacuous self-check that STRIPS the symbol's backticks from a copy of the doc text and confirms the requirement then fails to find it (so deleting the paragraph fails the suite instead of passing it). A test that only asserts "core EXPORTS the symbol" is always-true and worthless here — the symbol exists in code by construction; the thing at risk is the DOC naming it. (Groupline `test_core.js` §7's `REQUIRED_DOC_SYMBOLS = ['buildShareGrid','DIFFICULTY_EMOJI','guesses']` positive assertion + backtick-strip self-check is the worked example. Distinct from the base rule's symbol-existence cross-check — that guards a NAMED symbol going stale; this guards a REQUIRED symbol never being named at all.)
13. When a UI commits a state mutation SYNCHRONOUSLY but defers the re-render that would disable/replace/rebuild the triggering controls behind an animation or `setTimeout`, every control still live during that gap can re-fire the SAME action on the SAME (still-committed) state. A normal impatient double-click then double-applies an irreversible step — counts two mistakes, spends two turns, submits twice, deletes twice — silently corrupting a counter or budget that the pure logic computed correctly. The pure core is innocent; the bug lives entirely in the async UI seam, so core unit tests never see it. Two fixes, apply BOTH: (a) the instant the guess/action is submitted, mark an in-flight flag and re-entry-guard the handler (`if (inFlight) return;`), AND disable/neutralize the live control right then — before the deferred render, not inside it; (b) freeze the rest of the input surface for the same window (in Groupline, grid tiles and Deselect stayed clickable during the 420ms shake and could mutate the resolving selection and, via a synchronous `render()`, mint a fresh NON-disabled Submit button — the same class, second surface). Reset the flag on the next render/new-round. Guard the class with a regression test that runs the ACTUAL shipped UI script against a tiny fake DOM whose `setTimeout` QUEUES callbacks (so you control when the deferred render fires), fires a second click IN the gap, and asserts exactly one application — plus a NON-VACUOUS self-check that strips the guard and confirms the harness reproduces the double-apply (Groupline `test_core.js` §8 is the worked example). When you add more guards of the same shape (e.g. one per handler), a self-check that strips "the guard" by a bare first-match `replace(/if \(inFlight\) return;/)` will silently target the WRONG line and go vacuous — anchor each strip to its handler's context (`function onSubmit(){…}`) and assert the strip actually changed the source. Also make the freeze VISIBLE, not merely a silent no-op: a re-entry-guarded control that still LOOKS live (not greyed) is a "why didn't that do anything?" moment for the user — when you enter the freeze, set `disabled=true` on EVERY frozen in-play control at that instant (not just the one that triggered it; in Groupline the Shuffle/Deselect buttons stayed visually enabled while only Submit greyed), and add a regression assertion that reads each control's `disabled` during the shake window plus a non-vacuous fresh-board check that they start enabled (Groupline `test_core.js` §9(d)). (General "deferred re-render leaves a stale control able to re-fire the same mutation" class; any animate-then-render, debounce-render, optimistic-mutate-then-async-refresh, or disable-only-inside-the-callback UI is a candidate — distinct from every backend/data/docs class in rules 1-12.)
14. A headline RUNTIME property that the whole pitch rests on but that your automation CANNOT exercise (the classic: a single-file HTML game/app claiming "opens straight from disk, fully offline, no server, no CORS" — Playwright and browser-harness both BLOCK the `file://` protocol, so no interactive tool can prove it at a literal `file://` origin) must be pinned by a STATIC invariant test on the shipped artifact, not left to a one-off manual browser check that never runs again. For the offline-from-disk class: assert the HTML contains no `fetch(`/`XMLHttpRequest`, no `<script type="module">` or bare ESM `import ... from` (module fetches are CORS-blocked under `file://`), and no external HOST in any `src`/`href` (CDN script, remote font/stylesheet, `http(s)://` or protocol-relative asset) — a same-dir relative `src="core.js"` is fine and is NOT a CORS-guarded request. Strip comments before scanning so prose can't trip it, and add a self-check proving the remote-ref regex actually FLAGS an obviously-remote reference so a later regex slip can't make the assertion silently always-pass (Groupline `test_core.js` §6b is the worked example; verified non-vacuous by injecting a `fetch` + CDN `<script>` into a copy and watching it fail). The trap is that the dev loop serves over `http://` where a newly-added remote request still works, so the offline claim rots invisibly. (General "a runtime property the automation can't reach must be proven structurally on the artifact" class; distinct from rule 11's tested-but-not-demonstrated and rule 12's docs-vs-code drift — this is about a shipping-artifact invariant that no interactive test can cover.) COROLLARY — a BENIGN `http(s)://` LITERAL living INSIDE an inline `data:` URI (the classic: an inline SVG favicon/icon/background whose `xmlns='http://www.w3.org/2000/svg'` namespace ships un-percent-encoded in the data: URI) is a STANDING HAZARD to the offline scan, even though the precise `src=/href=`-anchored remote-ref regex correctly does NOT flag it today. It sits one edit away from breaking the invariant BOTH ways: a future edit that un-encodes more of the SVG or moves the namespace next to a quote, or one laxer offline-scan regex, turns that raw scheme literal into a FALSE-POSITIVE remote-ref match — OR it becomes the camouflage a genuinely-remote ref hides among (a real `//host` slips in unnoticed beside the "expected" namespace `http://`). Because the artifact then STILL parses and the icon STILL renders, nothing flags the rot. Cheapest durable fix, do BOTH: (1) carry NO raw scheme literal at all — percent-encode the namespace inside the data: URI (`http%3A%2F%2Fwww.w3.org%2F2000%2Fsvg`); the browser percent-decodes the data: URI back to the real `xmlns='http://www.w3.org/2000/svg'` before parsing the SVG, so the icon is byte-for-byte identical in effect; (2) add a static invariant asserting the whole shipped HTML contains ZERO raw `http://`/`https://` substrings (comments stripped — including HTML `<!-- -->` comments, the natural home for a prose mention of the real URL — so a documented mention can't trip it), with a self-check that the scan DOES flag an un-encoded namespace literal and does NOT flag the percent-encoded form, plus a POSITIVE check that the favicon's data: URI still percent-decodes to the real SVG namespace (so encoding the hazard away didn't break the icon). Verify non-vacuous by re-injecting a raw `http://` into the LIVE data: URI of a copy and watching the scan fail. This is CROSS-PROTOTYPE: any future single-file HTML artifact with an inline SVG data: URI (favicon, inline background, icon sprite) has the identical hazard, and a per-prototype test only guards the one that has it. (Groupline `test_core.js` §6c, with the favicon namespace re-encoded to `http%3A%2F%2F…` in `index.html`, is the worked example. Distinct from rule 14's core remote-ref scan — that catches an ACTIVE remote `src`/`href`; this closes the passive-literal escape hatch beside it.)
15. An OPTIONAL curated field whose PRESENCE is what a downstream quality bar keys on must reject its EMPTY/degenerate form at the validation gate, not silently accept it. The trap: a field is optional (omitting it is fine), so the validator's shape-check happily passes an empty container — `bait: {}`, `tags: []`, `rules: {}`, `overrides: {}` — but that empty value contributes NOTHING to the metric it appears to serve, so the author who wrote it (expecting it to satisfy the bar) is surprised later when the item is flagged too-easy / untagged / unconfigured. An empty declaration that LOOKS like a real one is worse than an omitted field: it reads as intent while carrying none. Fix at the domain boundary (the validator/constructor every path goes through, per rule 10): if the field is present it must be NON-EMPTY and well-formed, with a message that says exactly that ("declare at least one X, or OMIT the field"); omission stays legal. Add a regression test that the empty form is REJECTED and that a minimal non-empty form still PASSES (so the rejection doesn't over-reach into "reject the whole field"). (General "an empty optional field masquerades as a real declaration" class; distinct from rule 10's constructor-invariant — that's about a value that violates a range; this is about a shape that is technically valid but semantically vacuous, and about surfacing the mistake at authoring time instead of as a downstream surprise. Groupline `validatePuzzle` rejecting `bait: {}` with a §2 regression test is the worked example.)
16. A user/config-supplied string the user later READS BACK — whether it becomes a FILESYSTEM PATH SEGMENT verbatim (a category/folder name, an export subdir, a generated filename) OR is a pure DISPLAY/IDENTITY string echoed in output and compared for equality (a participant/person name, a label, a tag, a dictionary key) — must be validated for HYGIENE, not only for traversal/security. Rule 8's markers (separator, `..`, leading dot, absolute, empty/whitespace-only) all pass a name that is fully contained and undo-reversible yet still broken: SURROUNDING WHITESPACE (`" Torrents "` makes a folder literally named with the spaces; `" A "` vs `"A"` become two DISTINCT people who render a confusing `A pays  A  $3.00` line; `name != name.strip()`) and any NON-PRINTABLE / CONTROL character (`"foo\nbar"`, tab, NUL — a newline/invisible char inside a name; use `str.isprintable()`, which keeps the ordinary internal ASCII space so a legitimate multi-word `"My Docs"` / `"Mary Jo"` still passes). Reject both at the SAME validation gate every path goes through (per rule 10 — for a display name that gate is the domain constructor, NOT only the parser, so a directly-built object is rejected identically), with a message that names the fix ("use the trimmed name" / "use a plain name"); a curated name should be exactly what the user typed. The equality-collision harm is the reason this bites even when the string never touches the filesystem: two names that look identical behave as different identities (or, inverted, a padded key silently fails to match its unpadded twin). Add regression tests for each rejected form AND a positive test that an ordinary internal-space name still passes, so the hygiene check doesn't over-reach into rejecting all multi-word names. (General "curated string the user reads back needs hygiene, not just anti-traversal" class; distinct from rule 8 — that's containment/escape; this is a safely-contained-but-ugly/broken name — and from rule 15's semantically-empty optional field. `tidy._validate_category_name` rejecting `" Torrents "`/`"foo\nbar"` while accepting `"My Docs"`, and `settleup`'s `Expense` constructor rejecting `" A "`/`"foo\nbar"` participant/payer names while accepting `"Mary Jo"`, are the worked examples — caught in path-segment form THREE times in one heartbeat, then again in display-name form.)
17. A mode/subcommand that PROVABLY does not consume an optional pre-loaded input must not be gated on that input validating. The trap: a CLI/handler resolves and validates a shared optional resource (a config, a cache, a plugin manifest, a schema) up front — "so a bad one aborts cleanly before any work" — and only THEN dispatches to the chosen mode. But one mode (the classic: an `--undo`/rollback/repair/reset escape hatch) never reads that resource, so a corrupt/unsafe/absent input the user may not even be able to see blocks the very command meant to fix the mess. Dispatch the non-consuming mode BEFORE loading the input it doesn't use; load the optional resource only on the paths that actually need it. Add a regression test that the non-consuming mode SUCCEEDS with a deliberately broken/absent form of that input (and that the input's error never leaks into the mode's output). (General "an escape-hatch mode gated on an input it never reads" class; the recovery path is exactly when the shared state is most likely broken, so it's the worst thing to make a precondition. `tidy` dispatching `--undo` before loading `.tidy/config.json` — so a malformed in-folder config can't block the undo — is the worked example. Distinct from rules 7/8/10 which are about validating an input you DO consume; this is about not requiring one you DON'T.)

18. A COMMON, BENIGN, UNAMBIGUOUS byte-level artifact that real editors add to a user-authored text/JSON/CSV file — a leading UTF-8 BOM (`U+FEFF`), CRLF line endings, a trailing newline, a trailing comma the format tolerates — should be TOLERATED at the read/parse boundary, not rejected as if it were content corruption. The trap: the strict path is technically "correct" (a BOM-prefixed file IS rejected with a clean one-line error + non-zero exit, so it MEETS the clean-error contract and no verifier flags it), but a user whose editor silently wrote the BOM sees their perfectly-valid ledger refused with a baffling `Unexpected UTF-8 BOM` and has no idea their file is fine. Toleration is cheap and unambiguous: decode files with `utf-8-sig` (consumes one leading BOM, still raises on genuinely non-UTF-8 bytes) and/or strip one leading `﻿` before the empty-check and the `json.loads`/parse so BOTH the file-read path and any direct-text path are covered by one rule. Guard the class with a regression test that a BOM-prefixed VALID input parses/reports normally (exit 0), plus one that a BOM-ONLY input still routes to the ordinary empty-input error (the BOM is stripped, THEN the empty check fires — a BOM must not masquerade as content). Do NOT over-tolerate: this is only for artifacts that are unambiguous and lossless to drop; genuinely malformed content, wrong encodings, and non-UTF-8 bytes still take the clean-error path. Distinguish from rule 4 (that's "handle empty/garbage gracefully via the error path"); this is the inverse — an input that LOOKS slightly off but is actually fine and should SUCCEED, not error. (General "tolerate a benign editor-added artifact instead of rejecting valid content" class; the factory hit BOM tolerance independently in `subscription-sleuth` (CSV, tolerated) and `settleup` (JSON, initially rejected then fixed via `utf-8-sig` + leading-BOM strip with a §BOM regression test) — a repeat across prototypes, which is what earns a durable rule.)

19. A doc that FREEZES A LITERAL COPY of a command's real output (a README's fenced sample block showing `./run.sh` over the committed fixture, a `--help` transcript, an example session) must be BOUND to that real output by a byte-exact regression test, not hand-synced by eye. The trap is subtle because the block LOOKS right: a human freezing it silently strips trailing whitespace, collapses a run of spaces, or drops a blank line — invisible edits — while the real renderer emits them (the classic: a table whose final column is `ljust`-padded ends every header/row with trailing spaces that no human copies). Every number, row order, column name, and alignment byte can also drift when the code or fixture changes and nobody re-pastes the block. A set-membership check (e.g. "every cadence appears") is far too weak — it never compares the literal text. Guard the class with a test that EXTRACTS the frozen block from the doc (parse the first ```-fenced region) and asserts it `==` the real renderer's output over the committed fixture, comparing EVERY byte (trailing whitespace included); on failure the message says "regenerate the block from `<the command>`". Prefer ALSO fixing the source so the frozen copy a human naturally writes just matches: strip trailing whitespace per emitted line in the renderer (`"  ".join(cell.ljust(w)…).rstrip()`) — trailing spaces on a terminal line are never wanted — so the block and the output can't diverge on invisible padding, and add a direct invariant test that no rendered line has trailing whitespace. Make the byte-exact test NON-VACUOUS: feed it a synthetic block differing by a single trailing space and assert it is NOT equal (and the identical one IS). (General "a doc's frozen command-output literal drifts from what the command actually emits" class; `subscription-sleuth`'s README sample block, whose `ljust`-padded header emitted `NEXT DUE  ` while the frozen copy showed `NEXT DUE`, is the worked example — fixed by `rstrip`-ing each rendered line AND binding the block to `format_table` output with a byte-exact `FrozenSampleOutputTests`. 22. A doc's PROSE that describes an invariant must not claim a STRONGER guarantee than the test/code actually enforces. 23. A prototype's HEADLINE / flagship command example must not silently depend on a tool the prototype's own pitch promises NOT to require. The trap: the project advertises "no install / Python 3 standard library only / no dependencies", and every RUNNABLE path honours that — but a DOC EXAMPLE of a new feature reaches for a convenience tool that isn't stdlib and isn't on many machines (the classic: piping `--json` output into `jq`). 25. A grid/cell INDEX derived from a DOM EVENT FIELD or a LAYOUT-GEOMETRY READ (`evt.clientX`, `offsetX`, `touches[0].pageY`, `getBoundingClientRect().width/height`) can be `NaN` or `Infinity`, and a plain `idx < 0 || idx >= n` range check is ALL-FALSE for `NaN` — so the poisoned index sails straight past the guard into pure-core logic (`playDrop(state, col)`, an array write, a splice) and throws an uncaught error at a user-facing entry point. Two real sources, both reachable in a shipped single-file canvas game/app: (a) a malformed event whose coordinate field is `undefined`/non-numeric (`evt.clientX - rect.left = NaN`); (b) the genuine browser edge where an element measured mid-layout-transition has `getBoundingClientRect().width === 0`, so a scale factor `canvas.width / rect.width = Infinity` and `0 * Infinity = NaN`. This is the rule-4 garbage-input class ("verifiers try that first") specialized to the POINTER/canvas UI seam that the pure-core tests structurally can't see (the core is innocent, exactly like rule 13) — and it has a SECOND, compounding harm rule 4 doesn't name: if the handler stores that index into UI cursor/aim/selection STATE (`aimCol = col;`) BEFORE validating, the `NaN` POISONS every subsequent input, because arithmetic recovery is impossible — `Math.min(n-1, NaN) = NaN`, `Math.max(0, NaN) = NaN` — so the keyboard/aim surface stays dead until a full restart. Fix, apply BOTH halves: (1) validate the derived index with `Number.isInteger(idx) && idx >= 0 && idx < n` (NOT a bare `< 0 || >= n`; `Number.isInteger` rejects `NaN`, `Infinity`, AND non-integer floats) at EVERY entry point that can reach the core — the click/tap handler, the shared drop/commit helper, AND each keyboard handler — and BAIL before storing it, so cursor state is only ever assigned a validated integer; (2) read cursor state back through a `safe*()` coercer (`Number.isInteger(cur) ? cur : default`) in every handler that consumes it, so even a hypothetically-poisoned value snaps back to a valid default instead of staying dead. Guard the class with a regression test that drives the ACTUAL shipped inline UI script against a tiny fake DOM (per rule 13's harness pattern): fire a click with `clientX: undefined` AND one through a `getBoundingClientRect` returning `width: 0`, assert neither throws; then fire the documented keyboard drop/aim keys AFTERWARD and assert they still register drops (the cursor wasn't poisoned) and a later NORMAL click still drops (the guard didn't over-reach); plus a NON-VACUOUS self-check that strips the finite/integer guards from the source and confirms the malformed click THEN throws the core's `ValidationError` (so the harness genuinely reproduces the bug). (`chainfall`'s `onCanvasClick`/`doDrop` NaN-column crash — `Math.floor((px - PAD) / CELL) = NaN` reaching `Core.playDrop` — fixed with an `isValidCol` = `Number.isInteger` gate at all three entry points plus a `safeAimCol()` coercer, and pinned by `test_core.js` §9b, is the worked example. General "a NaN/Infinity index from an event/geometry read slips past a range check into the core, and poisons cursor state" class; distinct from rule 4 — that's generic empty/garbage at a CLI/file boundary — and from rule 13 — that's a deferred-render double-FIRE of a valid action; this is a single malformed read producing an out-of-domain index a naive comparison can't reject.)

26. An output that emits ONE ROW/UNIT PER STEP across a range DERIVED FROM DATA (the classic: a per-calendar-month activity sparkline, an hour-by-hour timeline, a per-bucket histogram, or a table that iterates `min(field)..max(field)` of some record field) is UNBOUNDED by construction — its length is set by the SPREAD of the data, not the COUNT of records — so a SINGLE outlier value blows it up: one stray 1970-epoch mtime (a `cp -p` from an ancient backup, a `touch -t 197001020000`, a misdated download), one far-future timestamp, or one huge/negative id stretches the range to decades/centuries and floods the terminal with hundreds or thousands of near-empty rows (`sediment`'s `month_sparkline` emitted **609** rows for a 53-year span and **1200** for a 100-year span from ONE epoch-0 file, almost all empty `·` rows, drowning the actual diary). It is not a crash and not garbage input — every value is individually valid and the code exits 0 — so rule 4 (empty/garbage → clean error) does NOT catch it, and neither does any correctness test; the output is simply UNUSABLE. This is the OUTPUT-side dual of rule 25's poisoned-index (an outlier value corrupting the RENDER extent rather than a core index). Fix: BOUND the emitted count with an explicit cap (`MAX_*_ROWS`) — when the data-derived range exceeds the cap, render only the most recent / most-active WINDOW and fold everything outside it into ONE honest summary row (`("… earlier", <count of folded items>, …)`), so no item is SILENTLY DROPPED — the outlier is acknowledged and the total still reconciles, it just can't dominate the layout. Keep the cap wide enough that ordinary inputs (and any committed sample/fixture) are UNAFFECTED and render byte-identically, so a frozen-output test (rule 19) still passes. Guard the class with a regression test that feeds a stray far-off outlier and asserts (a) the row count stays `<= MAX_*_ROWS`, and (b) the counts across all emitted rows SUM to the true item total (nothing dropped), plus a test that a within-cap span is uncapped and carries no summary row (so the cap didn't over-reach into normal output). (General "an output that emits one unit per step over a data-derived range is unbounded, and one outlier value floods it" class; `sediment`'s `month_sparkline` capped at `MAX_SPARKLINE_ROWS = 36` with a folded `"… earlier"` summary row, pinned by `test_sediment.py`'s `TestMonthSparkline` (stray-1970 stays ≤ cap, all files accounted for, short span uncapped), is the worked example. Distinct from rule 4 — that's a bad input taking the clean-error path; here every value is valid and the run succeeds, but the VOLUME of output is the defect — and from rule 25 — that's an outlier corrupting a core INDEX/cursor; this is an outlier corrupting the RENDER EXTENT.)

A HOST-LEVEL RESOURCE-EXHAUSTION condition — a full disk (ENOSPC), a saturated `/tmp`, no network for git, a dead/denied sandbox — can block the WRITE-dependent tooling a verifier and heartbeat depend on WITHOUT any product defect existing. The specific trap the factory has now hit repeatedly (groupline's pack-doubling heartbeat, chainfall's runaway, sediment): when the volume holding `/private/tmp` fills to 0 free bytes, the shell harness cannot allocate even the few bytes for its OWN per-command `.output` capture file, so EVERY Bash call returns `ENOSPC … tasks/*.output` and fails BEFORE the command runs — `node`, `git`, `grep`, `df`, `python3 -m http.server`, and Playwright (which must write an isolated temp browser profile via `fs.mkdtempSync`) all become un-runnable at once, and atomic file writes (the Edit/Write temp-file dance) fail too. This is NOT a prototype bug and NOT something a per-prototype test can guard; it is a verification-ENVIRONMENT failure, and the wrong reactions are (a) hard-failing the heartbeat as if the product were broken, and (b) deleting files OUTSIDE the factory tree — or shared `.output` capture files a CONCURRENT verifier may hold (lessons rule 5) — to force space. The auto-mode classifier correctly DENIES the shared-`.output` cleanup; respect the denial rather than working around it. Correct handling, in order: (1) confirm the condition is host-level and outside the tree (a `df`/`ls` that itself ENOSPC-fails is corroboration; the Read tool still works because it streams without a temp write, so use it to inspect files, tests, and data directly); (2) FALL BACK to Read-only structural verification — read the committed artifact, the test SOURCE, and the data by hand, and reason about what the (un-runnable) suite would assert — and RECORD the degradation honestly: name exactly which checks could not run (the cold-start `node test_core.js`, the `git diff` byte-check, the real-browser playtest, the screenshots) rather than claiming a green run you did not observe; (3) FLAG the host disk/`/tmp` for a future heartbeat to reclaim (it will intermittently block tooling until then); (4) if a brief window of space opens (another process frees bytes), immediately retry the write/commit — the condition is often transient. Above all, prefer engineering the prototype so a NO-TOUCH content non-goal is provable via the prototype's OWN test rather than only via `git diff`: groupline's "the existing 15 puzzles stay byte-identical" was originally checkable ONLY by `git diff 4a7dd6e~1 4a7dd6e -- data/puzzles.json`, which is exactly the tool ENOSPC kills — so the byte-identity went UNVERIFIABLE at the moment verification was wanted. The fix (a per-puzzle frozen content signature in `test_core.js` §14 — 16 words + 4 labels per settled board, normalized+sorted, non-vacuous both ways) makes the no-touch invariant self-checking via `node test_core.js` alone, so it survives degraded host tooling; git remains a corroboration, not the sole proof. (General "a host resource-exhaustion condition blocks write-dependent verification tooling; degrade to Read-only structural verification + honest degradation record + flag the host, never hard-fail and never delete outside the tree" class; groupline `test_core.js` §14 is the worked example of the byte-identity-without-git half. Distinct from rule 5 — that's per-run temp-dir ISOLATION to avoid cross-contamination between concurrent processes; this is what to do when the shared VOLUME those temp dirs live on is exhausted and the tooling itself won't run.)

A pointer hit-test that resolves a click to ONE OF TWO INTERSECTING interactive targets by NEAREST-DISTANCE (`vDist <= hDist` to pick a vertical vs horizontal crease/line/zone) silently MIS-RESOLVES at the exact intersection where both distances are ~equal — and a test/probe helper that aims at a target's GEOMETRIC CENTER can land on that intersection, masking the bug or making a whole class of input undrivable. At the exact crossing, `vDist == hDist`, so a bare `<=` tie-break deterministically picks one axis with NO way for the user to express the other — a click meant as the other fold becomes a SILENT WRONG action (in a fold puzzle, one that can dead-end the level). REFUSE the genuinely-ambiguous tie (return null / no-op) within a small tolerance band, so a click even slightly off the crossing resolves to the strictly-nearer axis and a dead-center click is a harmless no-op the player's tiny move corrects — a no-op beats a silent wrong action every time. The COMPOUNDING trap: a harness `gutterCoord`/`cellCenter`/`hitPoint` helper that returns the target's geometric center will, on a small board (2-wide/2-tall), sit ON the other axis's crossing and trip the same ambiguity — so the helper can't round-trip through the real hit-test for one axis, and a UI test built on it gets a FALSE result (a fold that "won't drive" or drives the wrong way). Guard the class with ONE regression test that drives the ACTUAL shipped UI on the SHARPEST board (the smallest one where the two axes' targets are maximally collided — a 2x2 for two crease axes) and asserts (a) the helper round-trips BOTH axes to the correct action (distinguish by the resulting state, e.g. grid dims: an h-fold shrinks rows, a v-fold shrinks cols), and (b) a click at the EXACT crossing is refused (state unchanged) — plus a NON-VACUOUS self-check that strips the crossing guard AND restores the naive centered helper and confirms the "other axis" click then resolves to the WRONG axis. Also confirm the refusal did NOT make anything unreachable: every level/target must stay drivable via the off-crossing helper (drive each certified solution end-to-end). (`foldup`'s `creaseAt` refusing the exact v/h crease crossing within `AMBIG=3`px + an off-crossing `gutterCoord`, pinned by `test_core.js` §16 on the 2x2 Level 1, is the worked example. General "nearest-distance hit-test between two intersecting targets mis-resolves at the tie, and a center-aiming test helper masks it" class; distinct from rule 25 — that's a NaN/Infinity index from an event read crashing/poisoning the core; this is a VALID index for the WRONG axis at a genuine geometric tie — and from rule 20 — that's a wrapping selector no-op'ing its own move; this is a two-target tie-break silently choosing the unintended target.)
