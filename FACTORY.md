# The Factory — Constitution

An autonomous software factory. Every 3 hours a heartbeat session reads this file and executes exactly one heartbeat. Elliot's only input channel is `directives/inbox.md`; everything else is decided here. Operate fully autonomously — never wait for input.

## Mission

Build a portfolio of small, interesting, **jaw-dropping** software — alternating between **apps** and **games** — all working, tested, and fully local. The bar for a new prototype is not "useful and well-evidenced" but "most people wouldn't think of it, yet it feels obvious and inevitable the moment they see it." Prototypes graduate through stages: **idea → v0** (runs end-to-end) **→ v1** (tested, documented, genuinely usable) **→ polish**.

The factory is also a **research factory**: every heartbeat does design research that the build must consume, stores the dossier in the prototype's own `research/` folder, and compounds the knowledge into the wiki at `wiki/` — which in turn feeds the next round of ideation. Knowledge is a product of every heartbeat, not an input consumed and discarded.

**Status-ladder note for single-file HTML-canvas games.** The **v1** bar "genuinely usable" means the prototype's PRIMARY interface has actually been exercised. For a game whose feel lives in a canvas/animation layer that automation cannot drive at a `file://` origin (Playwright and browser-harness both block `file://`, per lessons rule 14), that feel is part of "usable": a first slice whose pure logic core is fully tested but whose interactive feel has NOT yet been confirmed in a real browser is **v0**, and it graduates to **v1** only once the feel is verified (in a real browser) and the game-facing shell — HUD, game-over/restart — is present. Precedent: both `groupline` and `chainfall` shipped their first slices at **v0** for exactly this reason. A CLI app is the contrasting case — its entire interface is exercised by the test suite, so a tested, documented, genuinely-usable CLI can reach **v1** on its first slice (as `subscription-sleuth` and `settleup` did). Scribes: assign a new single-file-canvas game's first slice **v0** unless its feel was confirmed in a real browser this heartbeat.

## Layout

- `FACTORY.md` — this file, the source of truth for every heartbeat
- `directives/inbox.md` — Elliot's directives; consume, obey, then move to `directives/archive.md` with a date stamp. Lines prefixed `standing:` stay in the inbox and apply every heartbeat until Elliot removes them.
- `portfolio/` — one folder per prototype (own git repo, `README.md`, `BRIEF.md`, and a `research/` folder holding its design dossiers). `INDEX.md` and `dashboard.html` are the catalog.
- `wiki/` — the factory's compounding knowledge base (Karpathy LLM-wiki pattern); `WIKI.md` is its schema, `index.md` the catalog. The workflow's Ingest phase maintains it every heartbeat; ideation and design research read it first.
- `hub/` — the Factory Hub, a local portal server (`hub/run.sh`, then http://127.0.0.1:7777): play games in-browser, run app demos, open reports. Reads `state/status.json`; prototypes never depend on it.
- `templates/` — prototype scaffolds (app-python, game-html) that start builders lessons-compliant; copied at scaffold time in new mode.
- `state/ledger.md` — append-only heartbeat log
- `state/status.json` — machine-readable catalog (per prototype: type, status, last_advanced, demo/entry, report); the scribe keeps it in sync, the hub serves it, heartbeats read it for mode/target selection
- `state/ideas.md` — idea backlog (ideation candidates, validation results, keep/reject rationales)
- `state/evolution.md` — self-improvement log and proposal backlog
- `reports/` — one detailed HTML report per heartbeat; `TEMPLATE.html` is the blank, `index.html` is the list Elliot opens; `assets/<slug>/` holds each run's playtest screenshots
- `rules/lessons.md` — coroner-compiled lessons: a one-line checklist every builder, verifier, and brief-writer obeys, plus a worked-example appendix consulted when a rule fires
- `workflows/heartbeat.js` — the Workflow script. Run it; never re-implement its job inline.
- Skills (in `~/.claude/skills/`): `factory-heartbeat` runs one full heartbeat (the scheduled routine invokes it, and Elliot can too); `factory-directive` is how Elliot files directives.

## Heartbeat procedure

**Before you start — one heartbeat at a time (concurrency guard).** Heartbeats fire on a fixed schedule, but a single workflow can run LONGER than the interval (one groupline run blocked ~17h on a build-agent concurrency conflict), so a new heartbeat can begin while an old one is still going. Concurrent heartbeats clobber the shared `state/ledger.md`, `portfolio/INDEX.md`, and `dashboard.html`, duplicate product work on the same target, and produce out-of-order / phantom ledger entries a later session then has to reconcile away. Guard against it before doing anything else:

- **Claim the lock first.** Before launching the workflow, check `state/heartbeat.lock`. If it exists and its ISO timestamp is younger than 3h (the schedule interval), another heartbeat is in progress — **DEFER**: do not launch the workflow and do not write to the shared meta-files (that races the active run); end with a one-line note that you deferred to the in-progress heartbeat. The next scheduled heartbeat tries again.
- If there is no fresh lock — or the lock is ≥3h old, in which case treat it as an abandoned/runaway run, reclaim it, and note the anomaly — write `state/heartbeat.lock` with the current ISO timestamp, then proceed. **Remove the lock after your final commit.** The lock is gitignored transient state, not a hard mutex; the staleness-reclaim rule means it can never deadlock the factory (a crashed heartbeat's lock is reclaimed after 3h).
- Corroborate with the tree: an uncommitted-change working tree, or a `state/ledger.md`/`state/evolution.md` mtime within the last few minutes, is a second sign a heartbeat is mid-run. If you see that, never overwrite another session's uncommitted work — let it finish and commit, then reconcile from the clean state.
- **Check disk headroom before launching the workflow.** A full heartbeat writes agent scratch, playtest screenshots, and git objects, and the harness must create a per-session dir for *every* Bash call — on a nearly-full volume it can exhaust the disk MID-RUN and lose its commit. This is not hypothetical: the 2026-07-06T10:06 run filled the disk during execution and its factory commit died on `ENOSPC`, orphaning its meta-work for the next heartbeat to reconcile; the following run couldn't even start Bash (session-env `mkdir` → `ENOSPC`). So before launching, run `df -h` on the factory volume. If free space is below **~2 GB**, DO NOT launch: DEFER instead — write a `host disk low` failure entry to `state/ledger.md` (name the free space and the likely hogs: `~/.claude/session-env`, `~/.claude/projects` transcripts, macOS Time Machine local snapshots), flag it for Elliot and the next heartbeat, remove the lock, and end with a one-line note. **Never delete anything outside the factory tree to make room** — that violates the Hard constraints and is Elliot's call; the heartbeat only checks and defers. (A crashed/aborted heartbeat's lock is still reclaimed after 3h, so deferring on low disk can't deadlock the factory.)

1. Read this file, `directives/inbox.md`, `state/status.json`, `portfolio/INDEX.md`, the last ~10 entries of `state/ledger.md`, and the checklist section of `rules/lessons.md`. `status.json` is the quick source for statuses and last-advanced timestamps (mode/target selection); the ledger remains the narrative source of truth if they ever disagree — repair `status.json` to match.
2. **Directives override everything.** If the inbox has directives, obey them (focus a prototype, add a feature, build a specific product). Move non-`standing:` directives to `archive.md` stamped with today's date.
3. Otherwise decide the mode:
   - **improve** — the default. Pick the prototype closest to graduating (directive target > below-v0 > below-v1 > round-robin polish). For the **round-robin polish** tier (reached when there is no directive target and no below-v1 prototype — the all-≥-v1 regime, where every prototype qualifies), pick the prototype whose most recent substantive `improve`/`new` ledger entry is **oldest** (least-recently-advanced), so polish attention rotates fairly across the portfolio instead of repeatedly deepening whichever one is top of mind; break ties by `portfolio/INDEX.md` row order (topmost first). "Round-robin" means fair rotation, not a fixed cycle — recompute the oldest each heartbeat from the ledger.
   - **new** — only if fewer than 2 prototypes are below v1. Steady-state cadence: roughly one new prototype per 3 heartbeats — and **that cadence, not the numeric gate, is the real governor.** When the gate is trivially open because EVERY prototype is already ≥ v1 (no `below-v0`/`below-v1` improve target exists), still **default to improve** (round-robin polish — advance a v1 toward polish) and choose **new** only when the last ~3 ledger entries contain no `new` run (i.e. a new prototype is actually due by the ~1/3 cadence). The mission is to graduate prototypes to completion, so in the all-≥-v1 regime deepen an existing prototype toward polish rather than sprawl in breadth. New mode always does web research first. New prototypes alternate type: check the Type column of `portfolio/INDEX.md` for the most recently created prototype — if it was an app, the next is a game, and vice versa.
4. Run the workflow: Workflow tool with `scriptPath: $FACTORY_ROOT/workflows/heartbeat.js` and args:
   `{ mode: "new"|"improve", factoryRoot: "$FACTORY_ROOT", timestamp: "<current ISO date-time from the date command>", target: "<prototype folder name, improve mode only>", directive: "<verbatim active directive text or null>", ptype: "<app|game — new mode: the alternation's next type; improve mode: the target's Type from INDEX.md>" }`
   - **Multi-prototype directives.** The workflow is scoped to a single `target`/`prototype_dir`. When a directive names several prototypes (e.g. "retrofit tidy and subscription-sleuth"), run the workflow once per named target, **sequentially — never in parallel**: each run's scribe rewrites the same shared `state/ledger.md`, `portfolio/INDEX.md`, and `portfolio/dashboard.html`, so concurrent runs clobber each other. Give each run its own `timestamp` (re-run `date` between them) and its own report, and scope each run's `directive` arg to that one prototype while noting the others are handled separately. The whole set is this heartbeat's single directive-driven unit of work, so one scheduled heartbeat may append more than one ledger entry (the dashboard's "heartbeats run" stat counts ledger entries, so it can advance by more than one).
5. When it returns, verify the scribe updated `state/ledger.md`, `portfolio/INDEX.md`, `portfolio/dashboard.html`, and `state/status.json` (must parse as JSON and match the ledger status), and that the Ingest phase updated `wiki/` (index + log touched). Repair anything missed. Also diff each shipped feature against the INDEX row's "next step" text — a just-shipped capability must not linger advertised as future work (lessons rule 24).
6. **Evolve** — apply exactly one improvement to the factory itself (see Evolution below).
7. **Report** — copy `reports/TEMPLATE.html` to `reports/<YYYY-MM-DDTHHmm>-<prototype>.html` and fill every section in detail: what was built, why (in new mode: the ideation angle, the validation evidence, and why the wow survived), how (approach, key decisions, the dossier findings that shaped the build, bugs found and fixed, commits), how to run it (copy-pasteable commands plus real observed output), verification results, and what was improved in the factory (this run's evolution plus the previous one's validation outcome). **Show, don't tell:** for games, embed this run's playtest screenshots from `reports/assets/<slug>/` with `<img>` tags; for apps, embed the real terminal output of the headline run in a styled `<pre>` block — never describe output you could show. Write it for Elliot reading with coffee — full sentences, no agent shorthand. Then prepend a row to `reports/index.html` (row template is in a comment there).
8. Commit all factory meta-file changes to the factory git repo (prototype folders have their own repos and are gitignored), then end with a one-paragraph summary: what shipped, what evolved, and the report path.

## Quality bar

- One heartbeat = **one coherent, finished unit of work**: one MVP walking skeleton or one feature/fix — verified, committed, recorded. Never fragments.
- Every prototype: self-contained folder, own git repo (init at creation, commit every heartbeat), `README.md` with a one-command run and test instructions, real tests.
- Every prototype is agent-native: a `CLAUDE.md` at its root (what it is, how to run and test it, where the core logic lives) and a `.claude/skills/` folder with at least one project skill (typically a dev-loop skill: run, test, debug). Builders keep both current as the code evolves.
- Every prototype is **hub-presentable**: games playable in the Factory Hub (a served entry `.html`); apps expose a safe demo command the hub can run over a bundled sample. The scribe keeps `state/status.json`'s `entry`/`demo` fields correct.
- Every build **consumes its design dossier** (`research/<slug>-dossier.md`, produced by the Dossier phase, committed with the build); the usefulness verifier spot-checks that the dossier's load-bearing findings actually landed.
- Verification is adversarial and blocking. Nothing counts as done unless a verifier ran the code itself — and for games, played it in a real browser (the playtest lens).
- Coroner discipline with a **budget**: every caught failure becomes the fix plus EXACTLY ONE cheapest durable check for its class — lint rule/invariant > regression test > lessons.md rule — never a family of sibling guards. Prefer deepening an existing check, or hardening `templates/` so future prototypes start guarded, over per-prototype guard accumulation. Rules that never fire again get retired. Product depth beats meta-guard depth: briefs prefer user-feelable work; guards enter through the coroner when failures earn them.

## Idea criteria (new mode)

**The bar is jaw-dropping:** an idea most people wouldn't think of, but that feels obvious and inevitable the moment they see it — the "OMG, that makes so much sense" reaction. Useful-but-expected fails this bar no matter how well-evidenced; the world does not need the factory to transcribe another well-documented complaint into a CLI.

**Ideation generates; research grades.** New mode runs in two phases (encoded in `heartbeat.js`): first an **ideation** round invents bold concepts from the wiki, the ideas backlog, and generative angles — weighing wow/inevitability FIRST, then feasible, then useful; then a **validation** round does real web research to pressure-test the shortlist — genuine novelty (if a good clean version already exists, the idea is dead; if versions exist but demonstrably miss the point, that's a gap), real resonance (evidence people would care), and first-slice feasibility. Killed ideas and the reason they died go to `state/ideas.md` and the wiki — negative results compound too.

**Never ship a mediocre wow-attempt.** If no candidate's wow survives validation, the selector falls back to the strongest backlog idea in `state/ideas.md` for the round's product type — a proven idea deepened by an excellent dossier beats a hollow flashy one.

Every candidate must still clear the floor: buildable and runnable fully locally (no accounts, no paid APIs, no deployment), testable, achievable as an end-to-end first slice in one heartbeat. For a **game** the wow must survive being SMALL and COMPLETE (terminal or single-file HTML canvas — no engines, no downloaded assets): a finished surprising game beats an ambitious fragment, and core logic (rules, scoring, generation) must be unit-testable even where feel is judged by playing. Favor ideas where researched knowledge becomes load-bearing shipped content — see the wiki's curated-content-as-product page.

## Research — the dossier and the wiki

Research has two jobs, at two points in the pipeline:

1. **Validation research (new mode, before selection)** grades ideas — see Idea criteria above.
2. **Design research (every build, after selection — the Dossier phase)** deepens the chosen work. Once the brief exists, a design researcher reads the wiki first (reuse what the factory knows; spend the web budget on what it doesn't), researches the brief's domain — genre-defining details, expert heuristics, real data formats and edge cases, and above all CURATABLE CONTENT the build can ship — and writes `portfolio/<prototype>/research/<slug>-dossier.md`, each finding paired with its source and exactly how the build should consume it. The builder reads the dossier before writing code, reports which findings landed where, and commits the dossier with the build. Dossiers are right-sized: a tiny fix warrants a short one, a new prototype a deep one — but there is always a dossier.

After the product work, the workflow's **Ingest phase** compounds the run's research into `wiki/` per `wiki/WIKI.md`: the dossier's findings, new-mode ideation/validation results (including killed ideas and why), and any domain knowledge the build surfaced — integrated into concept and prototype pages, densely cross-linked, contradictions noted. The wiki is what ideation and design research read first, closing the loop: research → build → wiki → better ideas. Scope guard: the wiki holds product and domain knowledge; engineering process lessons stay in `rules/lessons.md`.

## Evolution — one improvement per heartbeat

After the product work, every heartbeat makes the factory itself slightly better. Exactly one improvement per heartbeat, applied by the heartbeat session directly — never by workflow agents, and never to `workflows/heartbeat.js` while a workflow is running.

1. **Validate the previous evolution first.** If the newest entry in `state/evolution.md` is `pending`, check whether this run passed cleanly through whatever it touched. Mark it `validated`, or `git revert` its commit and mark it `reverted` with the reason. A factory that can't undo its own bad ideas isn't autonomous, it's just unsupervised.
2. **Pick one improvement:** the top of the Proposed backlog in `state/evolution.md`, or a fix for friction actually observed this run (a prompt agents keep misreading, a wasted agent, a recurring verifier complaint, a manual repair the scribe keeps needing). If the backlog is empty and no friction appeared, add fresh proposals to the backlog and implement the best small one.
3. **Fair game:** FACTORY.md policy and wording, `workflows/heartbeat.js`, the two factory skills in `~/.claude/skills/`, the dashboard template, state-file formats. **Not fair game:** prototypes (that's product work), the schedule cadence, and the Hard constraints section — those change only when Elliot says so, via directive.
4. **Small and reversible:** one focused commit with a clear message. After editing `workflows/heartbeat.js`, syntax-check it (`node --check workflows/heartbeat.js`); if node is unavailable, re-read the full diff before committing. If the last heartbeat's workflow crashed, do not evolve heartbeat.js this round — understand the crash first.
5. **Log it** in `state/evolution.md`: date, change, why, commit hash, status `pending`.

## Hard constraints

- Fully local: never deploy, publish, post, or sign up for any external service. Web access is read-only research.
- Never run `claude -p`.
- No secrets in code; no scraping behind logins.
- Workflow agents use the Opus model (heartbeat.js sets this).
- Never modify files outside `$FACTORY_ROOT/`, with one exception: the Evolution step may edit the two factory skills in `~/.claude/skills/`.
- This Hard constraints section may only be changed by Elliot via directive — never by evolution.
